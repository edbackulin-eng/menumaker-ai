## ЕТАП 3 — підсумок (усе ✅)

- **4 рушії** (`layoutEngine` як `Record`, не `if/else` — щоб забутий рушій ловив компілятор, не рантайм): Modern (banner-two-column), Grid, Bistro (classic-elegant), Editorial. Кожен — 3 дерева (Web/PDF/PNG).
- **Знайдені й виправлені живим тестуванням баги**: обрізані ціни через `nowrap` на довгих укр. назвах; PNG мовчки викидав категорію (оцінка висоти по 2 колонках замість найвищої); `isLayoutEngine` мовчки кидав `grid` у `classic` (масив був неповний — замінено на `Record`, тепер пропуск рушія = помилка компіляції); Satori не вміє `dotted`-бордер (лідери → `dashed` скрізь); react-pdf падає на `italic` без italic-шрифта (курсив прибрано, замінено на muted-колір); фото з Pexels розмиті у Grid (фіксований `tiny`-розмір розтягувався — тепер розмір фото залежить від `layoutEngine`).
- **Типи закладів**: `business_type` в `menus` — **nullable без дефолту** (свідомо: NULL відрізняє «ще не обрав» від «обрав restaurant»). Вкладки на кроці Template, не окремий крок, не при реєстрації.
- **Пресети**: `menu_templates.engine` (колонка з CHECK), `business_types text[]` + GIN-індекс, `palette`/`typography`/`photo_policy` (jsonb).
- **Форма venue**: PATCH замінює `content` цілком — використано `updateItemPhotoUrl`-подібний патерн, автозберігає без затирання інших полів (перевірено clobber-баг).
- **styleSuffix на реальний тип** + кнопка «перепідібрати фото під тип» на Editor.
- **Провенанс фото**: відстежується, чи фото стокове чи завантажене вручну. Кнопка перепідбору чіпає ТІЛЬКИ стокові, власні завантажені (включно з legacy) — недоторкані.
- **Перемикач «меню без фото»**: для Modern/Grid/Editorial, рядок стискається до «назва + ціна» без місця під фото. Bistro і так без фото. Кнопка перепідбору ховається, коли увімкнено.
- **Валюта**: `resolveCurrencyDisplay` через `SYMBOLS_RENDERABLE_IN_EXPORT_FONTS` — правило на основі реального гліфа в шрифті, не хардкод-список. `$ € £` символом, `грн/zł/Kč` кодом.

**Відоме обмеження перевірки:** Claude Code не може рендерити PDF візуально (немає `poppler`), перевіряє тільки текстовий вміст через `unpdf`. Верстку PDF завжди підтверджує PO сам.

- `metadataBase` через `NEXT_PUBLIC_APP_URL` (одна точка, підставляється `localhost:3000` поки нема домену).
- `robots.txt`/`sitemap.xml` статичні, без БД. Закрито: `/dashboard`, `/menus` (візард), `/admin`, `/api`, `/auth`, `/design-system`.
- `hreflang` — тільки на лендингу (не в `[locale]/layout.tsx` — інакше розповсюдилось би на `/login`/`/dashboard`, де мовні альтернативи не мають сенсу).

- **noindex за замовчуванням** на `/m/[slug]` через `<meta name="robots">` (не `robots.txt disallow` — сторінка лишається доступною для сканування, інакше краулер не побачить саму директиву noindex). Рішення: краще увімкнути індексацію потім (легко, безпечно), ніж вимикати після того, як Google проіндексував сотні чужих закладів (довго, брудно).

- Відоме обмеження: гілка `generateMetadata` для 404-випадку на `/m/[slug]` технічно мертва (Next підставляє власний вбудований 404-шаблон, який сам ставить noindex) — результат той самий, але шлях коду не виконується. Не критично, названо вголос.

### Технічні виправлення перед деплоєм (юридичний блок)

Пріоритет за спаданням, виконується в цьому порядку:

**2.1 (найкритичніше) — видалення файлів Storage при видаленні акаунту.**
Факт: каскад чистив тільки БД; файли в `avatars`, `menu-uploads`, `menu-exports`, `menu-photos` лишались доступними за прямими URL безстроково (три з чотирьох бакетів публічні). Порушення ст. 17 GDPR, обіцянка видалення не виконувалась. Виправлення: перед/разом із видаленням БД-записів — видалення файлів з усіх чотирьох бакетів за префіксом користувача; тест «створити з файлами → видалити → перевірити 404».

**2.2 — видалення оригінального завантаженого файлу після успішного парсингу.**
Claude Code перевірив весь шлях коду перед виправленням: `original_file_url` пишеться один раз у `/api/menus/import`, більше ніде не читається; на невдачі парсингу файл уже видаляється тим самим запитом (`deleteMenuFileSafe`); у wizard-UI немає кнопки «назад до Import» (тільки кнопка Back браузера, яка веде на новий незалежний потік `/menus/new`, що не знає про старий `menu.id`). Висновок: можна безпечно видаляти оригінал одразу після успішного запису `content` — без впливу на UX, без потреби в «завантажте заново». Це частина data minimization, не окрема задача.

**2.3 — TTL на IP-адреси.** `api_rate_limits`/`auth_rate_limits` накопичувались безстроково. Ретенція 30 днів.

**2.4 — мінімізація в AI-запитах.** `suggestImprovements` слав `venue.address`/`venue.phone` в Anthropic без потреби для поради щодо меню — виключено з payload.

**2.5 — кука сесії.** `httpOnly:true` **перевірено і відхилено** — `useUser()`-хук (використовується скрізь: шапка, дропдауни) викликає `supabase.auth.getUser()` через браузерний клієнт `@supabase/ssr`, який читає сесію з `document.cookie` на клієнті. `httpOnly:true` зробив би це неможливим і зламав би стан «увійшов/не увійшов» усюди, де він рендериться на клієнті. Рішення: лишити `httpOnly:false` як прийнятий ризик, скоротити тільки `maxAge` з дефолтних 400 днів до 30. Застосовано в трьох місцях, де конструюється Supabase-клієнт (`src/lib/supabase/server.ts`, `src/lib/supabase/client.ts`, `src/proxy.ts`) — усі три мають отримати однакове значення, інакше сесія рефрешиться з різним TTL залежно від шляху коду.

### Атрибуція Pexels — підтверджено обмеження

Звужено формулювання: атрибуція «Photos provided by Pexels» лишається **тільки** у вікні вибору фото. На публічні меню, PDF, PNG, QR — не додається ніколи. Ліцензія Pexels атрибуції не вимагає; вимога їхнього API — помітне посилання в платформі, воно вже виконане тим вікном. Claude Code підтверджує грепом відсутність в `menu-render/`, `/m/[slug]`, `src/lib/export/`.

### /privacy, /terms — в роботі

Знайдено PO живою перевіркою `/register` (і суміжного `/login`) на localhost. Нижче — тільки фіксація, нічого з цього ще не виправлено.

### 1. КРИТИЧНО (юридично) — Google OAuth обходить згоду на Політику/Умови

Кнопка «Увійти через Google» на `/login` (і та сама кнопка на `/register`) одразу викликає `supabase.auth.signInWithOAuth()` і редіректить на Google consent screen — жодної перевірки чекбокса згоди немає (перевірено кодом: `src/components/auth/google-signin-button.tsx`, `handleClick` викликає OAuth без будь-якої умови). Юридично — для користувачів, які реєструються через Google, згода з Політикою конфіденційності й Умовами використання не фіксується взагалі, на відміну від email-реєстрації, де чекбокс тепер обов'язковий.

**Потрібно реалізувати** (не зроблено): або (а) окрема проміжна сторінка з чекбоксом перед редіректом на Google, або (б) чекбокс на самій `/login` поруч з кнопкою Google, що блокує кнопку до відмітки.

**Це блокер для реального запуску** — не виправляти пізніше «між іншим».

### 2. СЕРЕДНЬО — Помилки авторизації показуються тільки українською

Підтверджено скріншотом PO: повідомлення «Акаунт з таким email вже існує. Спробуйте увійти.» показується українською навіть коли інтерфейс на іспанській. Причина в коді: `src/features/auth/actions.ts` — рядки з текстами помилок хардкоджені українською напряму в Server Action, не йдуть через `next-intl` (`return { success: false, error: "Акаунт з таким email вже існує. Спробуйте увійти." }`). Той самий патерн у `src/lib/validations/auth.ts` (повідомлення `zod`-валідації теж хардкод-українською) — імовірно та сама проблема для «невірний пароль», «невалідний email» тощо, потребує окремої перевірки кожного повідомлення.

### 3. СЕРЕДНЬО — Cloudflare Turnstile завжди українською

Підтверджено кодом: `src/components/auth/turnstile-widget.tsx` викликає `window.turnstile.render(container, { sitekey: siteKey, ... })` без параметра `language` — Cloudflare API підтримує `language` (`auto` за замовчуванням, або конкретний код). Зараз віджет показує «Успіх!» українською незалежно від обраної локалі інтерфейсу. Потрібно прокинути в компонент проп `language`, синхронізований з поточною локаллю Next.js.
