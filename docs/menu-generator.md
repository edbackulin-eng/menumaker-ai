# Menu Generator — базовий потік (Stage 7)

Архітектура першого user-facing сценарію: імпорт файлу/тексту → AI-аналіз → перегляд/редагування користувачем → вибір шаблону → завершене меню.

## Маршрути (навмисно root-level, не `[locale]/...`)

Специфікація орієнтувалась на `app/[locale]/(dashboard)/menus/new/`, але `src/app/[locale]/` — порожній scaffold (лише `.gitkeep`, без сторінок, без middleware для визначення локалі). Усі поточні маршрути (`/dashboard`, `/login`, `/admin`) так само лежать на root-рівні. Погоджено з PO: wizard будується на root-рівні (`/menus/new`, `/menus/[id]/review|template|result`), консистентно з рештою застосунку; `[locale]` scaffold лишається недоторканим до окремого майбутнього етапу i18n-роутингу.

## Стан wizard'а — DB-backed, не React state

Кожен крок читає/пише `menus` напряму, тому оновлення сторінки на будь-якому кроці не губить прогрес:

1. **Import** (`POST /api/menus/import`) створює рядок `menus` одразу (`status='processing'`) — до того, як AI взагалі відповість.
2. **Review** (`GET /api/menus/[id]` + `POST /api/menus/[id]/confirm`) читає `content` (уже записаний Import-кроком) і зберігає відредаговану версію.
3. **Template** (`POST /api/menus/[id]/apply-template`) — фінальний крок.

### Навіщо `content_confirmed_at`, а не новий статус

`menus.status` — фіксований enum (`draft`/`processing`/`completed`/`failed`), навмисно без wizard-специфічних значень (Stage 2 проєктувала його як загальний lifecycle-сигнал, що використовується і поза wizard'ом). Але "AI щойно проаналізував, чекає підтвердження" і "користувач підтвердив, чекає вибір шаблону" — обидва мають `status='draft'` з непорожнім `content`; без додаткового сигналу неможливо визначити, який саме крок показати після reload. Тому додано `content_confirmed_at timestamptz` (migration `20260712090000`) — `NULL` до підтвердження, timestamp після:

| Стан           | `content`  | `content_confirmed_at` | `status`             | Крок     |
| -------------- | ---------- | ---------------------- | -------------------- | -------- |
| щойно створено | `{}`       | `NULL`                 | `processing`→`draft` | Import   |
| проаналізовано | непорожній | `NULL`                 | `draft`              | Review   |
| підтверджено   | непорожній | встановлено            | `draft`              | Template |
| шаблон обрано  | непорожній | встановлено            | `completed`          | Result   |

## Коли списуються кредити / безкоштовне меню

Списання (або споживання безкоштовного ліміту) відбувається **в момент успішного AI-аналізу** (`POST /api/menus/import`), не в момент фінального завершення wizard'а (`apply-template`). Свідомий відхід від буквального прочитання "при успішному завершенні потоку (`status='completed'`)" з початкового брифу:

- **AI-виклик — єдина платна дія** у всьому потоці; Review/Template/Result — це лише редагування вже отриманих даних, без додаткових AI-викликів.
- Відкладення списання до `apply-template` означало б дозволити необмежену кількість безкоштовних/неоплачених AI-аналізів для користувачів, які жодного разу не довели wizard до кінця (кожен покинутий на кроці Review імпорт — це реальні гроші, витрачені на Anthropic, без жодного контролю з боку системи кредитів).
- Список результатом AI-аналізу без переходу до `completed` — це вже реальна цінність для користувача (видно розпізнані категорії/страви), тому справедливо, що саме це і є "успіхом", який списує кредит.

**Виняток**: якщо AI повернув валідну (за схемою), але **порожню** відповідь (0 категорій/страв — нечитабельний чи порожній файл), кредит/безкоштовний ліміт **не** списується, попри те що сам AI-виклик формально "успішний". Це не те, за що користувач має платити — «успіх» тут визначається не лише валідністю JSON-схеми, а наявністю хоч одної розпізнаної страви. Реалізовано в `src/services/menu-generator/menu-creation-credit.ts` (`analyzeMenuWithCreditGate`): AI викликається _без_ кредит-гейту, перевіряється кількість страв, і лише тоді, коли `totalItems > 0`, атомарно списується кредит/безкоштовний ліміт через `consume_menu_creation_credit()` (migration `20260712091000`).

Ця логіка навмисно НЕ проходить через `src/services/ai/credit-guard.ts` (`runCreditedAiCall`, Stage 6) — та функція завжди списує платні кредити; тут потрібна інша гілка обліку (перші `freeMenuLimit` меню — безкоштовні, через `credits_balance.free_menus_used`).

### `FREE_MENU_LIMIT`

`src/config/menu-generator.ts`: `freeMenuLimit: 1`. У початковому брифі було 3; PO свідомо зменшив до 1 для старту (жорсткіший контроль витрат, поки реальні патерни використання невідомі).

## Парсинг файлів

| Формат | Бібліотека                               | Чому                                                                                                                                                                                                                      |
| ------ | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PDF    | [`unpdf`](https://github.com/unjs/unpdf) | Serverless-оптимізована збірка PDF.js, без нативних залежностей і без файлової debug-логіки при імпорті, на відміну від старішого `pdf-parse` — актуальна рекомендація для Next.js/serverless на момент реалізації етапу. |
| DOCX   | `mammoth`                                | Стандартний вибір для `.docx` → raw text, як і запропоновано в брифі.                                                                                                                                                     |
| XLSX   | `exceljs`                                | `xlsx` (SheetJS) має історію CVE (prototype pollution, DoS) у неактуальних версіях; `exceljs` — добре підтримуваний, без цього шлейфу, достатній для read-only парсингу завантажених користувачем файлів.                 |

**Excel — колонково-усвідомлений парсинг** (`src/services/file-parser/xlsx.ts`): на відміну від PDF/DOCX (суцільний текст), Excel вже структурований по рядках/колонках. Замість дампу значень комірок без роздільників, кожен рядок перетворюється на `" | "`-розділений текст (явна межа колонки, яку AI легко розпізнає), а назва аркуша зберігається як заголовок секції (аркуші часто відповідають категоріям меню).

## Storage

Приватний bucket `menu-uploads` (migration `20260712090000`), не публічний — оригінальні файли не роздаються напряму, лише читаються нашим бекендом. RLS-політики (`{user_id}/...` префікс шляху) — захист в глибину на випадок прямого звернення клієнта до Storage в майбутньому; сьогоднішній єдиний шлях доступу — service-role клієнт (`src/services/menu-generator/storage.ts`), який RLS обходить. `menus.original_file_url` зберігає шлях об'єкта в bucket, не публічний URL (bucket приватний) — коментар у міграції це явно застерігає.

## Помилки

- **Непідтримуваний тип файлу** — `422 unsupported_file_type`, перевірка до створення рядка `menus` і до завантаження в Storage.
- **Файл завеликий** — `422 file_too_large`, ліміт `MENU_GENERATOR_CONFIG.maxFileSizeBytes` (10MB, синхронізовано з bucket'овим `file_size_limit`).
- **Пошкоджений файл** (парсер кидає помилку) — `422 file_parse_failed` із загальним повідомленням; технічна помилка парсера в клієнтську відповідь не потрапляє.
- **Порожній/нечитабельний вміст** (парсер відпрацював, але результат — порожній рядок) — `422 empty_file_content`, до виклику AI.
- **AI нічого не розпізнав** (валідна, але порожня структура) — `422 nothing_recognized`, кредит не списується (див. вище).
- **Недостатньо кредитів** — `402 insufficient_credits`, перевіряється до початку парсингу/завантаження (`assertMenuCreationEligible`), щоб не витрачати ресурси на приречений запит.
- **apply-template до confirm** — `422 content_not_confirmed` (послідовність кроків wizard'а).

У кожному з цих випадків рядок `menus`, якщо вже створений, позначається `status='failed'`, а завантажений файл (якщо був) видаляється зі Storage (best-effort, `deleteMenuFileSafe`).

## Обмеження цього етапу

- UI шаблонів — лише впізнавані картки (назва + кольоровий swatch за slug), без реального дизайну кожного шаблону — деталізація дизайну шаблонів залишена для майбутнього етапу drag-and-drop редактора.
- Import — синхронний HTTP-запит (як і всі AI-виклики з Етапу 6), не фонова черга: клієнт чекає на відповідь під час усього циклу upload+parse+AI. Прийнятно для обсягу цього етапу; черга стане потрібною, якщо файли/навантаження суттєво зростуть.
- Немає списку існуючих меню користувача (Dashboard) — лише сам потік створення нового меню з фінальним посиланням на `/dashboard` (Етап 8).
