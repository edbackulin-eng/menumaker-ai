# Privacy / GDPR audit (Stage 15.6)

Internal record of the code-grounded audit that drove the Stage 15.6 GDPR
remediation (geo-block, cookie lifetime, upload auto-deletion, `/privacy` +
`/terms`). Every claim below was verified against the actual migration or
source file at the time of writing — re-verify before relying on it if this
doc is more than a few months old, since the schema evolves.

## 3. Cookies actually set in production

| Cookie                                       | Set by                        | Purpose           | Lifetime                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------------------------------- | ----------------------------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sb-<project-ref>-auth-token`                | This app, via `@supabase/ssr` | Session/auth      | **30 days** as of this stage (was the package default of 400 days — see `src/config/auth.ts`). `httpOnly: false` is a known, accepted risk: `useUser()` (`src/lib/auth/use-user.ts`) reads it from the browser Supabase client, which needs `document.cookie` access.                                                                                                                           |
| `NEXT_LOCALE`                                | This app, via `next-intl`     | Locale preference | 365 days (`src/i18n/routing.ts`).                                                                                                                                                                                                                                                                                                                                                               |
| Cloudflare Turnstile's own cookie(s), if any | Cloudflare                    | Bot-detection     | **Could not be independently confirmed from this sandbox** — `document.cookie` cannot see a cross-origin cookie Cloudflare's iframe/script might set, and the browser network-inspection tool used for this audit did not surface it either way. Treat Cloudflare's own cookie policy as authoritative; do not assume "no cookie" without checking Cloudflare's current documentation directly. |

No analytics or marketing cookies are set anywhere in the codebase — confirmed by grep, not assumption.

## 4. What erasure/portability actually do today

- **Erasure** (`DELETE /api/profile`, `src/app/api/profile/route.ts`): calls `supabase.auth.admin.deleteUser(user.id)`. The `on delete cascade` FKs (verified in every relevant migration) take `profiles`, `menus`, `payments`, credits tables, and `menu_exports` with it.
  **Known gap**: Storage _objects_ (avatars, menu-uploads, menu-exports, menu-photos/dish-photo caches) are governed by RLS policies (`on storage.objects for delete`), not by any trigger tied to `auth.users` deletion — confirmed by grepping every migration for such a trigger and finding none. Deleting an account today leaves orphaned files in Storage. This was **not** fixed in this stage (out of the confirmed scope — data-minimization here was upload-auto-deletion, not the account-deletion path) and must be stated honestly in the Privacy Policy's erasure section, and flagged again after this stage's work.
- **Portability**: no export endpoint exists. A user's data is manually available only by an admin querying the DB directly — no automated "download my data" flow.

## 5. Remediations implemented this stage

1. **Geo-block** (`src/config/geo-block.ts`, `src/proxy.ts`): `/login`, `/register`, `/forgot-password`, `/reset-password` return 307 → `/{locale}/region-unavailable` for visitors whose `x-vercel-ip-country` is in `EU_UK_COUNTRIES` (27 EU states + GB + EEA-non-EU [NO, IS, LI] + CH — 31 codes, PO-confirmed full list). `/m/[slug]` (public menu pages) is deliberately untouched. Only meaningful on Vercel; always a no-op on localhost (no header).
2. **Cookie lifetime**: `sb-*-auth-token` maxAge cut from 400 days to 30 (`src/config/auth.ts`, applied in all 3 Supabase client construction sites). `httpOnly` stays `false` — verified breaking change if flipped (see §3).
3. **Upload data minimization**: `src/app/api/menus/import/route.ts` deletes the uploaded source file right after a successful parse, and no longer writes `original_file_url` on that path (the column exists for the failure-cleanup path still, and as a legacy field).

## 6. Still open after this stage

- Storage orphans on account deletion (see §4) — not fixed here.
- No scheduled cleanup for `api_rate_limits`/`auth_rate_limits` rows keyed by IP or stale email (see §1) — not fixed here.
- No automated data-export/portability flow — not fixed here.
- Cloudflare Turnstile's own cookie behavior is unverified from this environment (see §3).

These are reflected honestly in `/privacy`'s rights section rather than glossed over.
